# AI Fashion Manager — Финальные требования MVP

> Версия 2.0 · Источник истины для разработки. Основано на исходном ТЗ (v1.1) + согласованные
> технические решения и уточнения. MVP — закрытая обкатка (1 пользователь + узкий круг по белому
> списку, 1–5 человек), не публичный сервис.

---

## 1. Цель и метрика

Проверить на 1 реальном пользователе + узком круге, что ядро даёт **адекватные и честные советы**
по трём задачам: купить ли вещь / что надеть / что докупить.

**Метрика успеха — не выручка**, а совпадение вердиктов системы с тем, что пользователь сам
считает правильным после рефлексии. Если ядро не убеждает на одном человеке — масштабировать нечего.

## 2. Бизнес-модель (определяет архитектуру)

Модель А: подписка ведущая, партнёрка — добавка.

- Вердикт «покупать ли вещь» принимается **независимо**; партнёрские/рекламные интересы на него
  **не влияют никогда**.
- Партнёрские деньги появляются только на шаге **«где купить выгоднее»** (Цель 3), после того как
  полезность вещи уже решена.

Обещание пользователю: «перестанешь покупать то, что не носишь, и будешь знать, что тебе идёт».

## 3. Границы MVP

**Входит:** профиль · гардероб (с неполным) · Цель 1 (ядро) · Цель 2 · Цель 3 · реактивный разбор
референсов/товаров · **реактивная оценка постов из телеграм-каналов** (пересылка) · изоляция
нескольких пользователей по Telegram ID, доступ по белому списку.

**НЕ входит (Фаза 2):** публичный доступ, регистрация, онбординг · биллинг · **автоматический
мониторинг телеграм-каналов/сайтов** (proactive AI Buyer) · админка/дашборды · мобильное приложение ·
Shopping Intelligence, Style Evolution.

## 4. Фундамент: профиль и гардероб

### 4.1 Профиль пользователя
- **Внешность:** цветотип и контрастность (по фото лица при дневном свете).
- **Силуэтный портрет:** телосложение (худощавое/среднее/плотное), пропорции на глаз, рост —
  **качественно**, без сантиметров и жёстких ярлыков типа фигуры.
- **Базовые данные:** пол, возраст, рост (ввод).
- **Образ жизни и дресс-код** (ввод).
- **Стилевые предпочтения:** копятся из диалога и реакций.
- **Локация** (координаты) — для погоды в Цели 2 (см. 6).

Причина качественного портрета: vision-модели делают точные измерения ненадёжно; ошибочная
цифра/ярлык подрывает доверие ко всем последующим советам.

### 4.2 Role-tagging фото — жёсткое требование (инвариант данных)
Каждое входящее фото классифицируется по роли; роль хранится в БД рядом с фото:

| Роль фото | Что извлекаем | Учит профиль внешности |
|---|---|---|
| **selfie** | внешность, силуэт + вещи | **да** |
| **outfit-reference** | только стиль и вещи | нет |
| **product-shot** | только характеристики вещи | нет |
| **flat-lay** | только характеристики вещи | нет |

Профиль внешности/силуэта учится **ТОЛЬКО на selfie**. При неоднозначности система **обязана
спросить** («Это ты или референс?»), а не угадывать.

### 4.3 Цифровой гардероб
Для вещи: категория, цвет, материал, сезонность, стиль, бренд, цена, фото.
Добавление: (1) фото отдельной вещи, (2) разбор лука (вытаскиваем все вещи разом).
**Обязательно работает на неполном гардеробе** — польза с ~10 вещей.

### 4.4 Актуальность гардероба (механизм)
- У вещи статус `active / archived / candidate` и поле `last_seen_at`.
- `last_seen_at` обновляется автоматически, когда вещь появляется в разобранном луке или в принятом
  образе «что надеть» — гардероб подтверждается в ходе обычного использования.
- **Периодическая сверка** (по расписанию): бот показывает 3–5 давно не всплывавших вещей —
  «ещё носишь?» → `оставить / в архив`. Закрывает и «сезонные напоминания», и «повод вернуться» (§9).

### 4.5 Хранение фото по роли (против захламления + гигиена ПД)
| Роль | Что храним долго |
|---|---|
| selfie | признаки внешности → в профиль; держим последние 3–5 селфи, старые блобы удаляем |
| product-shot / outfit-reference | атрибуты вещи + эмбеддинг; **оригинал удаляем** после извлечения (опц. мини-превью) |
| вещь гардероба (своя) | **одно** каноничное фото на вещь; дубли загрузок удаляются |

Чистка — при загрузке + периодическая (планировщик). Долгосрочно в базе — преимущественно
производные данные, не сырые фото.

## 5. Цель 1 — «Купить ли эту вещь» (ядро, реализуется первой)

- **Вход:** ссылка на товар / скриншот / фото; **в т.ч. пересланный пост из телеграм-канала**.
- **Оценивает:** сочетаемость с гардеробом · полезность (новые образы) · уникальность (нет ли
  дубля) · соответствие стилю и внешности · оправданность цены.
- **Выход:** вердикт + балл (0–100) + **обоснование «почему»** (structured output).
- **Поиск дублей:** вещь к покупке распознаётся, по сигнатуре считается эмбеддинг и через
  pgvector ищутся похожие вещи гардероба — они подаются в вердикт для оценки уникальности
  («у тебя уже три похожих свитера»). Без эмбеддера — мягкая деградация (вердикт работает,
  уникальность оценивается рассуждением модели по сводке гардероба).
- Цена — best-effort из ссылки/скриншота; не достали — вердикт без точной цены, с пометкой.
- Монетизации здесь нет; партнёрка не влияет.

## 6. Цель 2 — «Что надеть сейчас»

- **Вход:** запрос + повод (ввод) + погода.
- **Локация автоматически:** при первом запросе бот просит геолокацию кнопкой Telegram
  (`request_location`), сохраняет координаты в профиль и дальше тянет погоду сам (Open-Meteo).
  Команда «обновить локацию».
- **Учитывает:** погоду, повод/формальность, состав гардероба, что давно не носилось, предпочтения.
- **Актуальность (тренды):** учитывается короткая сводка текущих трендов (под сезон/пол/повод),
  чтобы лук был современным. Тренды — **ориентир, не в ущерб** тому, что идёт пользователю, и
  практичности (§8). Сводка кэшируется по TTL (тренды меняются медленно — экономия §15); источник —
  модель с веб-поиском, за провайдером `TrendProvider` (заменяем/отключаем в одном месте).
- **Выход:** готовый образ из имеющихся вещей с пояснением (и опц. «чего не хватает» — зацепка к Цели 3).
- Реализуется **после** Цели 1 (зависит от полноты гардероба).

## 7. Цель 3 — «Капсула и что докупить»

- Определяет пробелы относительно образа жизни/стиля.
- Строит **последовательность покупок** (следующая самая полезная вещь, не список из 20).
- **Выход:** карта пробелов + приоритетная следующая покупка + как капсула работает.
- **Генерация изображения капсулы:** Claude составляет визуальный промпт, генератор рисует
  **иллюстративный** концепт капсулы. Claude картинки не умеет — идём через OpenAI (`gpt-image-1`)
  за портом `ImageGenProvider`. Без ключа — капсула отдаётся текстом (мягкая деградация).
- **Здесь подключается партнёрка** («где взять выгоднее») — монетизация-добавка модели А.
- Требует зрелого профиля — реализуется третьей.

## 8. Сквозные принципы (NFR)

Честность · Тактичность (усиление достоинств, без унижения) · Практичность · Прозрачность
монетизации (деньги — на «где купить», не на «покупать ли») · Персонализация · **Язык вердиктов
подстраивается под язык пользователя** · **Актуальность:** советы учитывают текущие тренды как
ориентир, но никогда в ущерб тому, что идёт пользователю, и практичности.

## 9. Удержание (требование к архитектуре)

Заложить повторяющиеся поводы вернуться: ежедневное «что надеть» · прогон каждой покупки через
Цель 1 · **сезонные напоминания / сверка гардероба** (§4.4) · развитие профиля (бросить = потерять
накопленное). Реализуется через лёгкий внутрипроцессный планировщик.

## 9a. Память общения

Агент хранит историю диалога (роль + текст, привязка к `user_id`) и подаёт последние N реплик
модели для контекста — «та вещь, что скидывал вчера», преемственность советов. Окно — последние
N ходов (MVP); сжатие старого в резюме — позже. История удаляется по `/delete` (каскад).

## 10. Данные и изоляция

- Идентификация — **Telegram ID**, без регистрации/паролей.
- Профиль/гардероб/история привязаны к ID и **полностью изолированы** между пользователями.
- **`/delete`** — одна команда удаляет все данные пользователя (БД + блобы фото), с первого дня.
- Доступ — по **белому списку Telegram ID** (middleware отсекает чужих до бизнес-логики).

## 11. Технические решения (согласовано)

| Слой | Решение |
|---|---|
| Язык / бот | Python 3.12 · aiogram 3 (async, FSM для диалогов) |
| LLM + Vision | **Claude `claude-opus-4-8`** через **свой Protocol + Anthropic SDK** (тонкая обёртка) |
| Маршрутизация моделей | одна модель на старте; интерфейс готов к разведению задач по моделям позже |
| БД | PostgreSQL 16 + pgvector (изоляция по `user_id`, поиск дублей по эмбеддингам) |
| ORM / миграции | SQLAlchemy 2.0 async + Alembic |
| Хранилище фото | S3-совместимое (MinIO локально / Cloudflare R2 в проде) |
| Погода | Open-Meteo (бесплатно, по координатам) |
| Эмбеддинги (дубли) | Voyage AI за `EmbeddingProvider`; отключаемо (`none`) с мягкой деградацией |
| Тренды | Claude + web_search за `TrendProvider`, с кэшем по TTL; отключаемо (`none`) |
| Генерация картинок | OpenAI `gpt-image-1` за `ImageGenProvider` (Claude не умеет); отключаемо (`none`) |
| Память общения | таблица `messages`, последние N ходов подаются модели; удаляется по `/delete` |
| Планировщик | APScheduler (внутрипроцессный) — ежедневные/сезонные сценарии, чистка фото |
| Конфиг / секреты | pydantic-settings + .env; белый список в БД |
| Логи | structlog |
| Деплой | docker-compose, **один процесс**; без очередей/кэшей/балансировщиков/микросервисов |

**Переключение провайдеров/моделей:** `LLMProvider` / `WeatherProvider` / `StorageProvider` /
`EmbeddingProvider` / `TrendProvider` / `ImageGenProvider` / `ChannelSource` за Protocol → реестр
выбирает реализацию по env (`LLM_PROVIDER`, `EMBEDDING_PROVIDER`, `TREND_PROVIDER`,
`IMAGE_GEN_PROVIDER`, …). **Мульти-провайдер по факту:** рассуждения на Claude, генерация
изображений на OpenAI — разные порты, независимо заменяемы.
Смена провайдера/модели = правка в одном месте, без изменений бизнес-логики. Anthropic-специфичные
structured output и prompt caching используются напрямую (экономия).

## 12. Телеграм-каналы

- **MVP (реактивно):** пользователь пересылает боту пост/ссылку из любого канала → бот прогоняет
  через движок (Цель 1 «подходит/дубль» + Цель 3 «нужного типа вещь, которой нет»). Ноль
  инфраструктуры мониторинга.
- **Шов на будущее:** абстракция `ChannelSource`. Автоматический мониторинг до 5 каналов
  (MTProto-ридер + фоновый разбор) — **Фаза 2**, включается без переписывания движка.

## 13. Модель данных (черновик)

`allowed_users` · `users` (профиль + координаты + язык) · `photos` (роль, ключ S3, статус хранения) ·
`wardrobe_items` (атрибуты + эмбеддинг pgvector + статус жизненного цикла + `last_seen_at`) ·
`trend_cache` (сводки трендов по контексту + `updated_at`) · `messages` (история общения:
роль + текст, для памяти агента) · `style_preferences`.

## 14. Порядок сборки (= план обкатки)

1. **Фундамент:** бот + белый список + БД + хранилище + профиль/гардероб (фото + разбор лука) +
   планировщик + политика хранения фото.
2. **Цель 1** — ядро, проверка адекватности вердиктов (в т.ч. пересланные посты из каналов).
3. **Цель 2** (после роста гардероба) + геолокация/погода.
4. **Цель 3** + реактивный «где купить» (партнёрка).

## 15. Бюджет

~$15–40/мес на 1 пользователя; до ~$50/мес на 5 тестерах. Доминирует Claude; инфраструктура — копейки.
Рычаги экономии: prompt caching, компактная сводка гардероба, (позже) маршрутизация дешёвых задач
на меньшую модель.
